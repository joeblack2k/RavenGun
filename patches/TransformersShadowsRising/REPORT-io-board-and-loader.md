## 2. What the game is, and which executables matter

### 2.1 Roles of the executables — all **[measured]** by parsing both PEs and disassembling Shell.exe

**`Transformers2/Transformers2.exe`** (PE32, i386, 9 332 736 B) is **the game**.

* Imports: `DINPUT8.dll`, `d3dx9_43.dll`, `lua5.1.dll`, `WS2_32.dll`, `KERNEL32.dll`, `USER32.dll`,
  `WINMM.dll`, `d3d9.dll`, `DDRAW.dll`, `GDI32.dll`, `SHELL32.dll`, `ole32.dll`.
* **No `HID.DLL`, no `SETUPAPI.dll`, no `hidapi.dll`.** The gun is read only through DirectInput 8
  (`DirectInput8Create` is an imported string, and the strings `DirectInput init error.` /
  `DirectInput8 Create Error.` are present).
* Contains the whole `GAME_MSG_*` vocabulary (attract, stage, score, recoil …) — i.e. the game speaks the
  Sega shell message protocol itself.

**`shell/Shell.exe`** (PE32, i386, 1 438 720 B) is **the launcher/supervisor, and the process the
TeknoParrot core is injected into**.

* Imports: `d3d9.dll`, `d3dx9d_35.dll`, `DSOUND.dll`, `DINPUT8.dll`, `WINMM.dll`, `gdiplus.dll`,
  **`DK2WIN32.dll`**, `COMCTL32.dll`, `WS2_32.dll`, `IPHLPAPI.DLL`, `KERNEL32.dll`, `USER32.dll`,
  `GDI32.dll`, `ADVAPI32.dll`, `ole32.dll`, **`HID.DLL`**, **`SETUPAPI.dll`**.
* From `HID.DLL` it uses exactly four functions: `HidD_GetHidGuid`, `HidD_GetAttributes`,
  `HidD_GetPreparsedData`, `HidP_GetCaps`. From `SETUPAPI.dll`: `SetupDiGetClassDevsA`,
  `SetupDiEnumDeviceInterfaces`, `SetupDiGetDeviceInterfaceDetailA`, `SetupDiDestroyDeviceInfoList`.
  It imports **no** `HidD_GetFeature`/`HidD_SetFeature`; all device traffic goes through
  `KERNEL32!CreateFileA` + `KERNEL32!ReadFile`/`WriteFile` on a raw HID handle.
* From the NAS logs (measured, external evidence): `Mainthread - 261011.log` shows
  `Shell Version: 180605` → `Validated GameData directory exists` → `Closing down shell ready for game
  launch` → `Launched …\Sega\Transformers2\Transformers2.exe` → `MAINTHREAD : Sending Power up Credit`.
  So the shell validates the install, closes its own launcher window, starts the game and then supervises
  it (messages, credit, lamps, recoil).

**Which executable the TeknoParrot core is injected into:** `Shell.exe`. Evidence: `game.ini` has
`[Identify] Path = shell/Shell.exe, Size = 1438720` (i.e. `GamePath` is the shell), the profile's
`ExecutableName` lists `shell.exe` first, and `Shell.exe` itself launches `Transformers2.exe` as a child.
The core is a separate injected DLL, not linked into `Shell.exe` (no TP import exists). **Therefore the
core lives in the shell's process, never in the game's process** — which is exactly why `--route tp-shm`
cannot work for this title, and why the tidily-shaped TP shared-memory gun layout in the profile
(start `0x1`, trigger `0x2`, lever `0x10`/`0x20`, coin `0x40`, aim as a complement at offsets 12/16/20/24)
is *unused* at runtime.

**What the game does without the core / without the shell:** `Transformers2.exe` started on its own stays
on `SYSTEM INITIALIZING... LOADING..` for > 50 s **[measured, from the findings file; reproduced by the
earlier round, not by me — I did not start the game]**. It waits for the shell. So *the shell is
mandatory*; the core is not.

### 2.2 The gun I/O route — **[measured]** and complete

`CSAEBoard` (object `saebd.obj`, from `TF2_Gun_R.map`) does:

1. `DirectInput8Create(hinst, 0x0800, IID_IDirectInput8A, …)`
2. `CreateDevice(GUID_Joystick, …)` — **the first joystick of the system; no VID/PID, no name filter**
3. `SetDataFormat(c_dfDIJoystick)` (80-byte `DIJOYSTATE`)
4. `SetCooperativeLevel(hwnd, DISCL_NONEXCLUSIVE | DISCL_FOREGROUND)`
5. `EnumObjects(DIDFT_AXIS)` with a callback that sets `DIPROP_RANGE` to −1000…1000 per axis, then `Acquire`
6. Poll `Update()`; conversion `(1000 − value) * 255 / 1000` → internal 0…510 (left/top = low)

Axis use, as measured on the TV: **horizontal from `lY`, vertical from `lX`**; player 2 horizontal from
`lRx`, vertical from `lZ`. Buttons: DirectInput 0–3 → game buttons 0–3, DirectInput 5 → game button 4,
DirectInput 4 → game button 5.

**VID/PID: none is required, and none needs measuring. [measured]** The game imposes no filter. The only
VID/PID in play is *ours*: `0x1209:0x72F0` (vendor 4617 / product 29424, a pid.codes-style pair, not a
Sega ID). The real Sega SAE board's VID/PID is **irrelevant for the gun** and was never needed. If the
brief's "measure the VID/PID" step is followed literally it will produce a number that changes nothing.

Our board definition, read from the **live** `~/projects/ravengun/packaging/hid-boards.json` **[measured]**:


## 3. The shell's HID "IOBoard" — what it looks for, and the design for a virtual one

This is the part the brief expected to need a `uhid` board. Everything here is **[measured]** from
`Shell.exe` disassembled on the Deck (`objdump -d -M intel`, imagebase `0x400000`) plus the NAS logs;
where I extrapolate I say so.

### 3.1 The enumeration and its failure ladder **[measured]**

`InitIOBoard` (≈ `0x43b000`–`0x43b5a0`) does the standard SetupDi dance:
`HidD_GetHidGuid` → `SetupDiGetClassDevsA` → `SetupDiEnumDeviceInterfaces` →
`SetupDiGetDeviceInterfaceDetailA` → `CreateFileA` → `HidD_GetPreparsedData` → `HidP_GetCaps` →
`HidD_GetAttributes`. Its error strings, in order, are:

```
InitIOBoard : SetupDiGetClassDevs() failed - USB general failure?
InitIOBoard : SetupDiEnumInterfaceDevice() returned %d
InitIOBoard : Didn't find any HID collections
InitIOBoard : Couldn't find IOBoard device
InitIOBoard : SetupDiGetDeviceInterfaceDetail() returned %d - no USB connected?
InitIOBoard : Error reading Device PID and Version
InitIOBoard : HidD_GetCaps() failed!!
InitIOBoard : HidP_GetPreparsedData () failed!!
InitIOBoard : Initialised OK
```

Only `Couldn't find IOBoard device` ever appears in the logs — i.e. enumeration itself succeeds but no
device satisfies the identity test. `Initialised OK` never appears.

### 3.2 How the shell identifies the board **[measured — the question is now closed]**

There is a static table in `.data` at `0x55dab0`, six entries of stride `0x208`, terminated by a zero
first key (`keyA`):

| node | +0 `keyA` | +4 `keyB` | +8 name | meaning |
|---|---|---|---|---|
| `0x55dab0` | `0x0001` | `0x0005` | `GAMEPAD` | HID UsagePage Generic Desktop / Usage Game Pad |
| `0x55dcb8` | `0x0001` | `0x0004` | `JOYSTICK` | Usage Joystick |
| `0x55dec0` | `0x0001` | `0x0080` | `SYSTEM` | Usage Sys Control |
| `0x55e0c8` | `0x0001` | `0x0002` | `TRACKBALL` | Usage Mouse (=`0x02`) |
| `0x55e2d0` | `0x0001` | `0x0006` | `KEYBOARD` | Usage Keyboard |
| `0x55e4d8` | `0` | — | — | terminator |

The shell reads the device's UsagePage/Usage from its caps, looks the pair up here, and stores the
resulting name in the per-device record (offset `+0x64`). A device that does not match gets the name
`UNKNOWN` (`0x5511d8`). The **output-report dispatcher** (`0x43ae50`) then writes a fixed 3-byte report to
**every enumerated device whose resolved name is `GAMEPAD`**, using
`WriteFile(handle, buffer@0x13fd000, wOutputReportByteLength, …)`.

The 3-byte report is built at `0x43af90` (and again at `0x43b483`/`0x43b4bc`/`0x43b4e0`/`0x43b511`):

```
report[0] = 0x00                      ; no report ID
report[1] = byte at 0x13fcffa          ; source varies per call site
report[2] = byte at 0x13fd02b
```

**RESOLVED (static measurement, no bench): the `POLLING FLAGS` branch is DEAD CODE.** The identity
question therefore collapses, and the virtual board is simply a Game Pad-class HID device. Three
independent pieces of evidence, all from `Shell.exe`:

1. **The compared string can never appear in the field it is compared against.** After the table walk,
   `InitIOBoard` writes the resolved name into the record at `+0x64` and then does
   `strcmp(record[+0x64], "POLLING FLAGS")` (`0x43b39e`–`0x43b3d2`). The **only** writers of that field in
   the entire binary are the two stores in this function (`0x43b390`, `0x43b397`), and the only values they
   can produce are the five table names — `GAMEPAD`, `JOYSTICK`, `SYSTEM`, `TRACKBALL`, `KEYBOARD` — or the
   literal `UNKNOWN` (`0x5511d8`). That set is **disjoint** from `POLLING FLAGS`, so the `strcmp` never
   returns 0 and the `jne 0x43b3da` at `0x43b3d2` is **always taken**. The store
   `mov DWORD PTR ds:0x13fcff4, ebx` at `0x43b3d4` is **unreachable**.
2. **No table node can supply the string.** A full 4-byte-aligned scan of `.data` and `.rdata` for every
   dword pointing into the name region `0x533800`–`0x533d00` returns exactly five hits — `0x55dab8`,
   `0x55dcc0`, `0x55dec8`, `0x55e0d0`, `0x55e2d8`, i.e. the five nodes above. None is `0x5338c4`. The
   string `POLLING FLAGS` occurs exactly once in the whole binary: as the inline literal in this compare.
3. **Even if it executed, nothing reads it.** The slot `0x13fcff4` has exactly **one** xref in all of
   `.text` — the store itself, at `0x43b3d6`. There is no reader anywhere. The "IO board pointer" is
   vestigial, a leftover of an older design this build never consults.

**Consequence — the only live requirement.** The board must be the HID device that this same table
classifies as **`GAMEPAD`**: a top-level collection with **`HIDP_CAPS.UsagePage = 0x0001` (Generic
Desktop)** and **`HIDP_CAPS.Usage = 0x0005` (Game Pad)**. The shell then reaches it through the *output*
path (`0x43ae50`), which writes the fixed 3-byte report to every enumerated device whose resolved name is
`GAMEPAD`, with `nNumberOfBytesToWrite = HIDP_CAPS.OutputReportByteLength`. **No product string, no
serial number, no VID/PID and no report-descriptor string participates in the decision** — the
`HidD_GetAttributes` call is only used to log the PID/version, not to filter.

**Per-device record layout** (base `0x13fd068`, stride `0x68`), read from the code — this tells us exactly
which caps fields matter:

| offset | field | written by |
|---|---|---|
| `+0x1C` | device handle | `CreateFileA` on the SetupDi interface path |
| `+0x20` | `HIDP_CAPS.Usage` (u16) | `HidP_GetCaps` |
| `+0x22` | `HIDP_CAPS.UsagePage` (u16) | `HidP_GetCaps` |
| `+0x26` | `HIDP_CAPS.OutputReportByteLength` (u16) | `HidP_GetCaps` — **the `WriteFile` length** |
| `+0x60` | `PHIDP_PREPARSED_DATA` | `HidD_GetPreparsedData` |
| `+0x64` | resolved usage name pointer | the table above |

**Input is not per-record.** The `HIDioThread` state machine drives one global protocol object at
`0x1403888` (`mov ecx,0x1403888` before the receive/parse helpers `0x439fa0` and `0x43a120`), so with a
single accepted HID device present there is no ambiguity about which device is read.

### 3.2a The caps constant `0x110000`, resolved

`0x110000` is **not** a caps signature: it is **`HIDP_STATUS_SUCCESS` (`0x00110000`)**, the NTSTATUS that
`HidP_GetCaps` returns. Sega's log message `InitIOBoard : HidD_GetCaps() failed!!` is simply a misnomer
for a `HidP_GetCaps` failure.

This also disposes of the "read `0x47ff50`" step in the earlier draft: **`0x47ff50` is not a function, it
is an import thunk.** The whole neighbourhood is the tail of the IAT-thunk block:

| thunk | import | used for |
|---|---|---|
| `0x47ff50` | `HID.DLL!HidP_GetCaps` (`jmp ds:0x488058`) | caps + the `HIDP_STATUS_SUCCESS` check |
| `0x47ff56` | `HID.DLL!HidD_GetPreparsedData` (`jmp ds:0x488064`) | failure logs `HidP_GetPreparsedData () failed!!` |
| `0x47ff5c` | `HID.DLL!HidD_GetAttributes` (`jmp ds:0x488060`) | "Error reading Device PID and Version" |
| `0x47ff62` | `HID.DLL!HidD_GetHidGuid` (`jmp ds:0x48805c`) | start of the enumeration |

(Cross-checked against the IAT slot addresses resolved from the import table: `0x488058` =
`HidP_GetCaps`, `0x48805c` = `HidD_GetHidGuid`, `0x488060` = `HidD_GetAttributes`, `0x488064` =
`HidD_GetPreparsedData`.)

### 3.3 The unlock/handshake protocol — **statically harvested in full**

`HIDioThread` (`0x43b5a0`) is a jump-table state machine: `mov eax,[0x1403884]`, `cmp eax,0xc`,
`jmp DWORD PTR [eax*4+0x43ba30]`. The jump table was dumped (14 dwords at `0x43ba30`), which pins every
state to its body. Four helpers do all the I/O:

| helper | what it really is | source |
|---|---|---|
| `0x43af90` | **build + send**: `report[0]=0`, `report[1]=[0x13fcffa]`, `report[2]=[0x13fd02b]`, then `0x43ae50` = `WriteFile` of `OutputReportByteLength` bytes to every device whose resolved name is `GAMEPAD` | **GEMETEN** |
| `0x439fa0` | **register a deadline**, not a receive: reads `QueryPerformanceCounter` and stores `start + N·ticks_per_ms` on the protocol object `0x1403888` (`+0x08/+0x0c` start, `+0x10/+0x14` remaining) | **GEMETEN** |
| `0x43a120` | **deadline check**: returns `1` when the elapsed time has reached the deadline, else `0`. Every reply state does `call 0x43a120; test al,al; jne <reset>`, so **a missing or late answer resets the whole handshake to state 0** | **GEMETEN** |
| `0x43ad80` | **input poll**: walks the same device records, and for the `GAMEPAD`-class one does `ReadFile(handle, ptr, 0xF, …)` — i.e. **15 bytes**, into the caller's buffer (`0x13fd030` for the state machine) | **GEMETEN** |

**The transform, corrected and verified.** The earlier draft had `ROL8`; the loop counters are `dl=7`,
`dl=6`, `dl=3` with a `dec`-then-body-then-test structure, so they are **7, 6 and 3** rotations:

```
forward(x, k) = ROL3( ROR6( ROL7(x XOR 0x92) XOR 0x35 ) XOR 0xA7 ) XOR k      # 0x43aee0, key from [esp+4]
inverse(y, k) = ROR7( ROL6( ROR3( y XOR k ) XOR 0xA7 ) XOR 0x35 ) XOR 0x92     # 0x43af40, key from AL
```

(`ROL7` = `ROR1`; rotations are plain 8-bit rotations.) Verified two ways: `inverse(forward(x,k),k) == x`
for all 256 `x` and several `k`, **and** a round trip against the code's own constants — the derived
UNLOCK1 byte goes back to `0x74` and the UNLOCK2 byte back to `0x09` (see the table). Implementation and
round-trip test: `tool-tsr-calc.py`.

**The complete harvest.** `sent` = the exact 3 bytes the shell writes; `deadline` = the `push` immediate
handed to `0x439fa0`; `answer` = what the board's **input report** must contain for the state to advance
(offsets are into the 15-byte input report, `input[12]` = `0x13fd03c`).

| state | body | sent bytes | deadline | required answer | hinges on | source |
|---|---|---|---|---|---|---|
| 0 `IOBOARD_INITIALISE` | `0x43b5b6` | *none* | retry `1000 ms` | — | `[0x140386c] != 0`, i.e. `InitIOBoard` reached `Initialised OK`; otherwise retries forever | **GEMETEN** |
| 1 `IOBOARD_IDREQUEST1` | `0x43b5f7` | `00 74 E0` | `1000 ms` | `input[12] = 0xB0` (checked in state 3) | — | **GEMETEN** (stores read out) |
| 3 `IOBOARD_IDREQUEST1_REPLY` | `0x43b642` | *none* | — | as above | `input[13]` is forward-transformed with key `0x74` and stored at `0x13fd064` — **stored, never compared** | **GEMETEN** |
| 2 `IOBOARD_IDREQUEST2` | `0x43b6b1` | `00 09 E1` | `1000 ms` | `input[12] = 0xB1` (checked in state 4) | — | **GEMETEN** |
| 4 `IOBOARD_IDREQUEST2_REPLY` | `0x43b6fc` | *none* | — | as above | `input[13]` forward-transformed with key `0x09`, stored at `0x13fcff0` — **stored, never compared** | **GEMETEN** |
| 5 `IOBOARD_UNLOCK1` | `0x43b76d` | `00 E0 F0` | `1000 ms` | `input[12] = 0xB2` (checked in state 7) | byte = `inverse(inverse(0x74,0x69),0x46)`; `0x13fcff2` is written exactly once (state 1) so it is still `0x74` here | **AFGELEID** (computed from the code; round-trip checked) |
| 7 *(no log line)* | `0x43b7cb` | *none* | — | as above | — | **GEMETEN** |
| 6 `COMMAND_UNLOCK2` | `0x43b803` | `00 CA F1` | `1000 ms` | `input[12] = 0xB3` (checked in state 8) | byte = `inverse(inverse(0x09,0xE9),0x3B)`; `0x13fd029` written once (state 2) | **AFGELEID** (same) |
| 8 *(`Unlocked OK`)* | `0x43b861` | *none* | — | `input[12] = 0xB3` | **also** requires `input[11] == 0x15` **and** `[0x13fcff3] != 0`, else it jumps straight to state 13 (done) | **GEMETEN** |
| 9 `COMMAND ENABLE KEYPAD` | `0x43b989` | `00 00 82` | `1000 ms` | `input[12] = 0xB4` (checked in state 10) | **reachable only if `[0x13fcff3] != 0`** | bytes **GEMETEN**, reachability **AFGELEID** |
| 10 *(`Keypad Enabled OK`)* | `0x43b9cf` | *none* | — | `input[12] = 0xB4` | on success → state 13 (done) | **GEMETEN** |
| 11 `COMMAND_USER_SEND_VERSION` | `0x43b8cb` | `00 00 96` | `1000 ms` | `input[12] = 0xB5` (checked in state 12) | **UNREACHABLE**: no code anywhere writes state `0xB` | bytes **GEMETEN**, unreachability **GEMETEN** |
| 12 *(`Got Redone Version %02d.%02d.%04d`)* | `0x43b911` | *none* | — | `input[12] = 0xB5`, then version = `(input[13]>>4).(input[13]&0xF).(input[14])` | — | **GEMETEN** |
| 13 | — | — | — | — | terminal: sets `[0x1403870]=1` and stops | **GEMETEN** |

**Reachability, measured.** The state variable `0x1403884` has exactly **16 xrefs in the whole binary**
(absolute-only addressing, so the scan is complete): one read at the dispatcher and fifteen writes. The
values written are `0, 1, 3, 2, 4, 5, 7, 6, 8, 9, 0xC, 0xA, 0` (reset) and `0xD`. **No site writes `0xB`**,
so the version query is dead code in this build. `0x13fcff3` has exactly 2 xrefs: the read in state 8 and
a single write at `0x43bbde`, which is

```
43bbca: push "CabinetSKU"        ; 0x533c14
43bbd9: call 0x441260            ; config lookup
43bbde: mov ds:0x13fcff3, al     ; = the ExternalKeypad setting
```

— i.e. the keypad state is gated on the shell's own configuration, not on the board. The neighbouring
lookup writes `0x13fcff8` from `("InputOutput", "DirectInput")`, which is the shell's DirectInput toggle
used by the poll path.

**So the handshake the board must satisfy is four exchanges, all with one magic byte at `input[12]`:**

```
shell -> board: 00 74 E0        board -> shell: 15-byte input report, byte[12] = 0xB0
shell -> board: 00 09 E1                        byte[12] = 0xB1
shell -> board: 00 E0 F0                        byte[12] = 0xB2
shell -> board: 00 CA F1                        byte[12] = 0xB3   -> "Unlocked OK" -> done
```

Input-report bytes 0–10 are **never read** by the handshake (only offsets 11–14 are touched at all), so
the board may send zeros there; the report must merely be **15 bytes** so that the shell's
`ReadFile(…, 15, …)` can consume it.

### 3.3a What could **not** be obtained statically — the real bench questions

1. **Whether Wine delivers HID input reports to `ReadFile` at all in this prefix.** Everything above
   assumes `/dev/uhid` becomes visible through Wine's HID stack to `SetupDi`/`HidD` *and* that `ReadFile`
   on that handle returns input reports. If Wine exposes the device to `SetupDi` but not to `ReadFile`, the
   handshake stalls after IDREQUEST1 with the reply never arriving. **This is the one route-level risk and
   the highest-value thing the run can show.**
2. **The lamp / billboard / recoil output path.** The poll function `0x43b470` emits further 3-byte reports
   from flag-driven sources (`0x13fcffc` → `00 [0x13fcffa] [0x13fd02b]`, `0x13fd024` → `00 [0x13fcf50]`,
   `0x13fd020` → `00 [0x13fcf53] [0x13fcf52]`, `0x13fd060` → `00 [0x13fcf54] [hi|0x40]`). **Which lamp or
   motor this is meant to drive is not derivable from `Shell.exe`** — it is the real board's contract. A run
   tells us the sizes and cadence; what we *want* the lamps to do is an owner decision.
3. **`input[11] == 0x15`** — needed for the keypad branch, and its meaning (a bitmap? a capability byte?)
   is not determinable from `Shell.exe`.
4. **Whether the handshake buys anything the owner wants.** The game is playable without it today; the
   payoff is lamps, the external keypad and hardware recoil. Not a static question.
5. **A register-relative write to the config byte `0x13fcff3` cannot be excluded by construction**, but the
   only three references to its 4-byte neighbourhood (`0x13fcff0`) are one byte-write by the handshake
   itself, the direct read in state 8 and one read pair in the status publisher — so no base-pointer write
   exists. Stated as a caveat, not a doubt.
6. **No chicken-and-egg problem was found.** Every gating value is either a constant from the code
   (`0xB0`–`0xB4`), a config byte, or the timeout — none of them is produced by the board's own answer. The
   transformed `input[13]` values are stored and never compared, so they cannot deadlock the handshake.

### 3.4 The `uhid` design, concretely

**Already built — do not rewrite.** `re\_pgg\loader-src\ravengun\iobridge\hid_board.cpp` **[mirror, but the
file is present in the live tree as well]** contains a complete `UhidBoardDevice`:

* `/dev/uhid`, `O_RDWR | O_NONBLOCK | O_CLOEXEC`
* `UHID_CREATE2` with `name = board.device_name`, `uniq = "ravengun-board"`, `bus = BUS_USB`,
  `vendor`/`product`/`version` from the board record, and the report descriptor from
  `hid_board_descriptor()`
* `UHID_INPUT2` for each frame, report from `hid_board_report()`
* `poll_output()` handles `UHID_OUTPUT` (counted) and **answers `UHID_GET_REPORT` with
  `UHID_GET_REPORT_REPLY / err = EIO` and `UHID_SET_REPORT` with `err = 0`** — otherwise Wine blocks for
  seconds
* `UHID_DESTROY` on close

Report descriptor and report, byte-exact from the code:

* Descriptor = `05 01 09 04 A1 01` (Generic Desktop / **Joystick** / Application), then
  `05 09 19 01 29 <button_count> 15 00 25 01 75 01 95 <button_count> 81 02` plus a padding item
  `75 01 95 <8 − button_count%8> 81 03` when `button_count % 8 ≠ 0`, then per axis
  `05 01 09 <usage> 16 <min lo hi> 26 <max lo hi> 75 10 95 01 81 02`, then `C0`
* Input report = button bitfield (`ceil(button_count/8)` bytes, little-endian bits) followed by each axis
  as little-endian `int16`, **no report ID**. For the SaeGunBoard shape (16 buttons, 4 axes) that is
  **2 + 8 = 10 bytes**.
* Axis usage order: `hid_board_hid_usage()` maps `X,Y,Z,RX,RY,RZ` → HID usages `0x30…0x35`; evdev codes via
  `hid_board_evdev_axis()`.
* `/dev/uhid` is root-only by default; `packaging/udev/71-ravengun-uhid.rules` already grants
  `KERNEL=="uhid", SUBSYSTEM=="misc", TAG+="uaccess"`, installed with `sudo scripts/udev-ravengun.sh --apply`.

**What a virtual *IO board* needs — now settled by §3.2, not conjecture:**

1. A HID top-level collection with **UsagePage `0x0001` / Usage `0x0005` (Generic Desktop / Game Pad)**.
   The existing descriptor's Application usage is `0x04` (Joystick), so this needs its own descriptor
   variant: `05 01 09 05 A1 01 …` instead of `05 01 09 04 A1 01 …`, not a reuse of the gun's.
   **No product string, serial number or VID/PID is consulted** — that possibility is now excluded by
   evidence, not by guesswork.
2. An **output report** of exactly `OutputReportByteLength` bytes (the shell writes the whole buffer and
   passes the caps value as the length), payload `00 <a> <b>` — the first one being `00 74 E0` (§3.3).
3. An **input path** that `ReadFile` can poll, plus the IDREQUEST/UNLOCK/version/keypad dialogue in §3.3,
   with the transform applied.
4. A **`HidD_GetAttributes`-visible PID and version** — but only because the shell *logs* an error when
   they are missing; **the values are not compared against anything** (the record keeps no PID/version
   field, and no branch in `InitIOBoard` reads one). Ours (`0x1209`/`0x72F0`, version 1) are usable as-is.

| item | status |
|---|---|
| Read/write API set, usage table, opcode strings, report IDs/lengths, transform constants | **measured from `Shell.exe` (read-only)** |

## 5. Dongle / integrity — measured, and deliberately not "left alone"

Per the corrected rules this is in scope for me, so here is the measurement rather than a hand-off.

* `Shell.exe` imports `DK2WIN32.dll` and contains the strings `DK2 driver not installed.`, `DK2#2653`,
  `DONGLE : Valid Key Found`, `DONGLE : MainThreadDongleScan: Security OK / Security Failed / failed stage 1`,
  `ERROR! NO SECURITY KEY FOUND`, `Scanning for Security Key..`, `SecurityDisabled`, `SecurityKey`.
  This is the Dinkey Pro ("DK2") USB dongle path, plus the shell↔game security handshake
  (`SHELL_MSG_SECURITY_AUTHENTICATE sent %02x %02x %02x %02x`, `GAME_MSG_SECURITY_CHALLENGE`).
* **Every** session on the NAS logs `DONGLE : MainThreadDongleScan: failed stage 1` — and the game still
  starts, plays, scores and offers continues (`GameStateMachine - 261011.log`: two players, scores, health,
  `GAME_MSG_TRIGGER_RECOIL`, "flashing BOTH lamps", `GAME_MSG_CONTINUE_OFFERED`).
* `shell/Game.ini` ships from Sega with `[Debug] SecurityDisabled=1`, `NoVerify=1`, `Forceinp64=1`,
  `CleanInstall=1`, and `ShellData.ini` ships `Freeplay=1`. That is the likely reason the failed scan does
  not block.
* `SHELL_MSG_CHALLENGE data = …` appears every ~10 s in the running session and never terminates the game.

**Conclusion [measured]:** this title needs **no** dongle emulation, no `dongle.json`, and no `[Dongle]`
section — consistent with `patches/STAND.md` counting it as `dongle: nee`. The only dongle-adjacent code
worth owning is the **IO-board** unlock dialogue in §3.3, which is a fixed keyless transform and not a
secret-key check. If the shell's second dongle stage ever turns up (`failed stage 1` implies a stage 2),
that is a *future* measurement, not a current blocker — and it can only show up on a longer session.

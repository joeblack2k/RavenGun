## The family in one paragraph

Eleven dumps, **three different mechanisms** that all get called "the dongle", and they must not be conflated:

1. **Sega keychip / `amDongle`** — the game or the daemon talks to a keychip dongle. This splits into **two
   generations**: the older bit-banged API (`amDongle Ver.0.12`, 2007 — `amDongleInit`, `amDongleIsAvailable`,
   `amDongleReadEeprom`, `amDongleReadSram`, `amDongleChipInfo`) carrying an EEPROM/BuSRAM **region** structure,
   and the **keychip** generation (2009–2018) which adds `amDongleSetupKeychip`, `amDongleGetRegion/GameId/
   ModelType/PlatformId`, and the `keychip.appboot.*` / `keychip.billing.*` / `keychip.tracedata.*` /
   `keychip.ssd.proof` namespaces.
2. **The region / piece-table answer** that TeknoParrot's profiles expose as `DongleRegion` + `PcbRegion`. That
   is what our `dongles/region-pcb` type mirrors, and for LGI/LGI3D/LGS it is already `enforced: false` — the
   game asks, reads, and does not gate on it.
3. **The SEGA Game Shell's Dinkey DK2 key** — a completely different thing, in `Shell.exe`, with its own
   `[Debug] SecurityDisabled=1` bypass and a staged scan. It shares nothing with (1).

The measured sub-finding that matters most for cost: **the 1190000-byte `*_Table.dat` files are per-game
encrypted blobs, not a shared table plus a key.** All six are exactly 1190000 bytes; they differ from each other
in ~99.6% of bytes, uniformly across the whole file, from byte 0; and `gzip -9` output (1190218) is *larger*
than the input for every one of them. Calibration: `cmp` of a file against its own copy reports 0. And the
table filename is the Sega **game id** (`SBUH` LGI, `SBWB` LGI3D, `SBYR` Transformers, `SBRZ`/`SBTF` Medaru,
`SDDV` TNXK0O~C; Let's Go Safari's `gameid.txt` reads `SDAX`, which is why LGS has no table). So the tables
cannot be synthesised and cannot be derived from one another — but they are probably a **non-item**, because
TeknoParrot runs these titles with only a region and a pcb id.

## The single biggest unknown in this family

**Whether the keychip/`amDongle` path is *enforced* anywhere in this family at all.** Every measured data point
currently says it is not: LGI, LGI3D and LGS are `enforced: false` and playable; HOTDSD is playable with no
keychip and its daemon merely retries; and Medaru No Gunman's actual failure (`3001 RAM DATA IS BAD` /
`3003 ROM HAS CHANGED`) measures as the **EEPROM** path — `eep.bin` is 0 bytes, and the `3001` strings in the
binary belong to CRI/ADX audio, not to the keychip. If that holds across the family, then the expensive
`sega-keychip` / `amDongle` shim is **not needed for any of the eleven titles**, and the whole family reduces to
(a) the region answer we already have, (b) EEPROM/BuSRAM **data** (Medaru, and the `arcade::_sArcadeBackup`
geometry in LGJ/LGJS), and (c) getting the titles that are unmeasured to a first run. That is a completely
different, much cheaper work item than "build a keychip emulator".

It is also cheap to settle, and it is the reason every "proposed test" column above has a **wrong-answer**
control rather than only a success criterion: for each title, change the answer we already give (a wrong region,
`aantal`/count zero where applicable, `amDongleIsAvailable()` false) and see whether the game notices. A title
that does not notice its dongle is wrong cannot be blocked by it.

**The one thing that is genuinely unmeasurable with what we hold — and therefore the honest second unknown** —
is **what stage 2 of the Game Shell's DK2 scan asks.** All four `Dongle - *.log` files, 27 sessions over five
days, contain exactly one line: `MainThreadDongleScan: failed stage 1`. The text `stage 2` appears nowhere in any
log; the only file on the share that contains it is `Shell.exe` itself. So the scan always aborts before we can
see what it would have asked, and the `sega-scan` descriptor type stays a framework until someone traces
`Shell.exe` past that branch.

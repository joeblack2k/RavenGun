# TeknoParrot-I/O onderzocht voor een eigen IO-brug (onderzoek, 2026-10-09)

Doel: begrijpen welke I/O-kaarten en protocollen de games van de eigenaar verwachten en hoe TeknoParrot (TP) invoer aanlevert, zodat ravengund later per game "het juiste dialect" kan spreken. Alleen interoperabiliteit; geen omzeiling van licentie, dongle of keychip. Elke bewering is gemarkeerd: [gelezen] = rechtstreeks in broncode, configuratie of een niet-ingepakt bestand gezien; [afgeleid] = mijn conclusie of onzeker.

Bronnen die ik echt las:
- https://github.com/teknogods/TeknoParrotUI (master, commit 3829d81, 2026-10-08) en de branch net8-migration (commit 250c1f0, de Linux/.NET 8-poort). Beide met `git clone --depth 1` in de scratchpad gelezen; licentie GPL-3.
- https://github.com/teknogods/OpenParrot (commit fc8ba63, 2026-09-11), GPL-3.
- Lokaal: `GameProfiles/*.xml` en `Metadata/*.json` in de TP-runtime; de dumps onder `~/mnt/spidernas_emulation/Teknoparrot/` (alleen `file`, `strings`, `objdump -p`, `readelf`, tekst- en logbestanden); `~/.local/state/ravengun/logs/tpui-*.log`.

Kernconclusie [afgeleid, goed onderbouwd]: de open TP-code beschrijft alleen de kant van de UI: een gedeeld geheugen van 64 bytes en een JVS-pipe. Wat de game zelf aanroept (FTDI, HID-bord, wajvio, COM1, mxjvs) wordt in de gesloten TP-kern (TeknoParrot.dll, ElfLdr2) vertaald. Geen van onze negen games staat in OpenParrot. Het transport is dus makkelijk na te bouwen; de moeilijke, onbekende laag is de game-kant per kaart.

## 1. Hoe TP invoer bij de game krijgt

Architectuur [gelezen: TeknoParrotUi/Views/GameRunning.xaml.cs, TeknoParrotUi.Common/Pipes/ControlSender.cs, Jvs/JvsHelper.cs, SerialPortHandler.cs]
- De invoerlisteners (InputListenerRawInput.cs, ...DirectInput, ...XInput) vullen statische arrays in `InputCode`: `PlayerDigitalButtons[]` (Test, Service, Coin, Start, Button1..6, Up/Down/Left/Right) en `AnalogBytes[32]` (2 bytes per kanaal: hoge byte op index 2n, lage op 2n+1).
- Kanaal A, gedeeld geheugen: `JvsHelper` maakt `MemoryMappedFile "TeknoParrot_JvsState"`, 64 bytes. Een `ControlSender`-subklasse, gekozen in een switch op `EmulationProfile` (GameRunning.xaml.cs rond regel 540-760), vult die elke 15 ms (`SleepTime = 15`) vanuit `Transmit()`.
- Kanaal B, JVS-pipe: `SerialPortHandler.ListenPipe("TeknoParrot_JVS")` (GameRunning.xaml.cs:967) maakt een named pipe (Windows) die de game als seriële poort ziet. Het verwerkt JVS-pakketten (sync 0xE0, escape D0 CF -> D0, D0 DF -> E0) met `JvsPackageEmulator.GetReply` op een 10 ms-raster. Seriële modus is 115200 8N1 (SerialPortHandler.ListenSerial).
- Onder Wine/Proton (net8-migration, `Tools/ProtonPipeHelper/pipehelper.c`) maakt een Windows-hulpprogramma in de prefix de echte named pipe en de echte named file mapping, en spiegelt ze via TCP naar de UI en via `Z:\dev\shm\TeknoParrot_JvsState` naar `/dev/shm`. Het kopieert byte 0 synchroon vóór het eerste antwoord (anders race bij een warme game). [gelezen]
- Game-kant, open voorbeeld: OpenParrot `OpenParrot/src/Functions/Ring_amLib/amJvs.cpp` hookt `CreateFileA/W`: opent de game "COM4" (voor sommige games COM2), dan wordt dat `\\.\pipe\teknoparrot_jvs`; ook GetCommState, SetCommState, GetCommTimeouts, SetCommMask, SetupComm, PurgeComm, ClearCommError, GetCommModemStatus, EscapeCommFunction worden gehookt en nep beantwoord. Dezelfde file mapt `TeknoParrot_JvsState` als `int*` (voor o.a. force feedback op offset 8 en verder). [gelezen]
- Onze logs [gelezen: tpui-*.log]: in 21 sessies met "*** GAME CONNECTED ***" staat steeds "game->TPUI total 0 bytes". De ElfLdr2-games verbinden dus wel met de pipe maar sturen er geen JVS-bytes over; hun invoer komt alleen via het gedeelde geheugen. Dit past bij de tot nu toe onbevestigde invoerroute in STATUS.md. [afgeleid: welke sessie bij welke game hoort, niet per log uitgezocht]

Indeling van de 64 bytes [gelezen, per Pipes/*.cs]
- Offset 0: "game verbonden"-vlag. `JvsPackageEmulator` schrijft 1 bij OP_ADDRESS (0xF1), 0 bij OP_RESET (0xF0). Offset 4-7: bij nieuwe profielen versie/vlaggen (alleen in `Tests/` gezien, niet voor onze games). Offset 8: 32-bit bitveld `Control`. Offset 12 e.v.: analoge waarden, per profiel anders. De rest is per profiel gereserveerd of leeg.
- WartranTroopers (Halo, Tomb Raider, Rabbids; WartranTroopersPipe.cs): bits 0x1 Test, 0x2 Service, 0x4 Coin1, 0x8 Coin2, 0x10/0x20 menu omhoog/omlaag (Button5/6), dan per speler vijf bits: Start, Trigger (Button1), Option (Button2), Shoulder (Button3), Sense (Button4); P1 begint bij 0x40, P2 bij 0x800, P3 bij 0x10000, P4 bij 0x200000. Bytes op offset 12..19: P1X, P1Y, P2X, P2Y, P3X, P3Y, P4X, P4Y (elk 1 byte). Let op: de profielnamen voor Halo zijn Trigger/Reload/Grenade, maar de pipe-opmerkingen heten Trigger/Option/Shoulder; de bitpositie volgt de Button-index. [gelezen]
- RawThrillsGUN (Jurassic Park, Terminator; RawThrillsGUN.cs): 0x1 Test, 0x2 Service, 0x4 Coin1, 0x8 Coin2, P1 Start 0x10, Trigger 0x20, Grenade 0x40, Reload 0x80; P2 dezelfde vier op 0x100-0x800; 0x1000/0x2000 volume omhoog/omlaag. Bytes op offset 12 (P1X), 16 (P1Y), 20 (P2X), 24 (P2Y). [gelezen; de byte-breedte volgt uit de C#-overload `Write(long, byte)`, afgeleid]
- TimeCrisis5 (TC5Pipe.cs): 0x1 Test, 0x4 Service, 0x8 Coin, 0x10 trekker, 0x20 gunknop, 0x40/0x80 linker/rechter pedaal, 0x100/0x200/0x400 omhoog/omlaag/enter (P2Button1-3). Offset 12 = X, 16 = Y. [gelezen]
- TransformersShadowsRising (...Pipe.cs): 0x1 P1 Start, 0x2 P1 trekker, 0x4 P2 Start, 0x8 P2 trekker, 0x10/0x20 hendel aanval/verdediging, 0x40 Coin. Bytes op 12, 16, 20, 24 uit AnalogBytes 0, 2, 4, 6. [gelezen]
- LuigisMansion (LuigisMansion.cs): bits P1 Start 0x1, knop 0x2, hendel 0x4; P2 0x8/0x10/0x20; Test 0x100, Select 0x200, Service 0x400; "scherm uit" 0x10000 (P1) en 0x20000 (P2). Op offset 12 een enkel 32-bit woord: byte 0 = P1Y, byte 1 = P1X, byte 2 = P2Y, byte 3 = P2X. [gelezen]
- LGS (Let's Go Safari; LGSPipe.cs): schrijft alleen offset 12 (stuurwiel). Knoppen en de rest komen via echte JVS-pakketten. LGS is de enige game van de eigenaar waarvoor de JVS-pipe de hoofdrol heeft. [gelezen]

JVS-emulatie (`Jvs/JvsPackageEmulator.cs`, `JvsHelper.cs`, `JVSPackets.cs`, `JVSIdentifiers.cs`) [gelezen]
- Behandelde commando's: F0 reset, F1 adres, 10 identificatie, 11 commandorevisie, 12 JVS-versie, 13 communicatieversie, 14 functielijst, 15 hoofdbord-ID, 20 schakelaars, 21 munten, 22 analoog, 26 extra schakelaars, 2E hopper, 2F hertransmissie, 30/31 muntaftrek, 32/37 algemene uitgangen, 33 analoge uitgang, 34 tekstuitgang, 36 uitbetaling; 70 en 78-80 (Namco-specifiek, genegeerd) plus een Taito-reeks. Antwoord: node, lengte, status 01, rapport 01, data, checksum, met escapes.
- Standaard-node: comm 0x10, JVS 0x20, commandorevisie 0x13, 14 schakelaarbits, identificatie "SEGA CORPORATION;I/O BD JVS;837-14572;Ver1.00;2005/10", twee spelers, twee muntsleuven, 8 analoge kanalen van 10 bit, 20 algemene uitgangen. Voor LGS (EmulationProfile `LGS`): identificatie "SEGA CORPORATION;I/O BD JVS;837-14895;1;1;FE MODE;2005/10", 1 speler, 0x16 schakelaarbits, 16 algemene uitgangen, JVS 0x30. Analoog antwoord: per kanaal `AnalogBytes[2i]`, `AnalogBytes[2i+1]`.

Lightgun-coördinaten, schaal en inversie [gelezen: InputListenerRawInput.cs rond regel 1690-1850; net8: Mouse/GunAnalogMath.cs]
- Beeldpositie wordt eerst een factor 0..1 (venster- of schermgrootte). Daarna `x = minX + factorX * (maxX - minX)`, afgerond; `xAxisMin/Max` en `yAxisMin/Max` uit het profiel. Bij 16 bit (`Use16BitAnalog` of `HighResolutionAxis`) worden bereiken binnen 0..255 met 257 vermenigvuldigd. Onze profielen: overal 0..255, behalve Luigi's Mansion (x 3..252, y 6..250) en geen 16 bit.
- `InvertedMouseAxis = true` (Halo, JP, Terminator, TC5, Luigi, Tomb Raider, Rabbids): X komt in `AnalogBytes[0]` (speler 1), Y in `[2]`, links/boven = 0. `false` (Transformers): X wordt `~x` in `[2]`, Y wordt `~y` in `[0]`, dus 255 aan links/boven. Luigi: Y in `[0]`, X in `[2]`, niet gecomplementeerd. Spelers 2, 3, 4 gebruiken indices 4/6, 8/10, 12/14.
- De profielen noemen dat "P1 Gun X = Analog0" (Halo, JP, Terminator, TC5, Tomb Raider) of "Analog2" (Transformers, Luigi), met `AnalogJoystickReverse` op de Y-as. `P1RelativeUp/Down/Left/Right` zijn de relatieve-modus-knoppen; `Use Relative Input` en "Player n Relative Sensitivity" (8) horen daarbij.

EmulationProfile en I/O-dialect [gelezen: EmulationProfile.cs, GameRunning.xaml.cs, 158 waarden in de lokale profielen]
- Gezinnen: (a) echte JVS-pipe met een profielspecifieke node (SegaJvs, LGS, TaitoTypeX*, NamcoPokken, Xiyangyang, enz.); (b) alleen gedeeld geheugen met een eigen indeling (WartranTroopers, RawThrillsGUN, TimeCrisis5, TransformersShadowsRising, LuigisMansion, enz.); (c) aparte emulatortypen met eigen pipes (TeknoVegas, TeknoS11/S21/S22/S23, TeknoViper, Dolphin, RPCS3, ...). Voor (b) bepaalt het profiel alleen de bitindeling; wat de game aan hardware verwacht staat nergens in het profiel.
- WartranTroopers dekt 51 lokale profielen, waaronder Halo, Tomb Raider en Rabbids. Het is dus een generieke "4-spelers shooter"-indeling, geen Halo-specifiek I/O-dialect. RawThrillsGUN dekt 19 profielen (o.a. JP, Terminator, Walking Dead, Aliens Armageddon). [gelezen, geteld met grep]

InputMapping-namen [gelezen: JoystickMapping.cs]: Test, Service1/2, Coin1/2, P1Button1..6, P1ButtonUp/Down/Left/Right/Start, hetzelfde voor P2 (en JvsTwoP1/P2... voor spelers 3 en 4), Analog0..15, P1..P4LightGun, P1..P4RelativeUp/Down/Left/Right, ExtensionOne1.. (extra knoppen).

RawInput-lightguns op Linux [gelezen: net8-migration, TeknoParrotUi.Common/InputListening/Mouse/EvdevMouseListener.cs, EvdevInterop.cs, GunAnalogMath.cs, LINUX_SETUP_GUIDE.md]
- De Linux-poort leest `/dev/input/event*` zelf. Relatieve muizen worden opgeteld op een virtueel canvas van 1920x1080; absolute apparaten (lightguns, tabletten) worden via `EVIOCGABS` (ABS_X/ABS_Y, min en max) lineair naar 0..1 gezet. Daarna dezelfde omrekening naar spelunits als op Windows (GunAnalogMath = bit-voor-bit port). Nog niet in de poort: vensterbegrenzing in windowed-modus. Een niet-gebonden muis wordt aan spelers toegewezen op ontdekkingsvolgorde; gebonden apparaten gaan via het `/dev/input/by-id`-pad of `eventN`. Dit verklaart de eventN-afhankelijkheid uit STATUS.md.

## 3. Wat OpenParrot (GPL-3) herbruikbaar heeft

[gelezen: OpenParrot/src/Functions/*]
- Wat er is: `Ring_amLib/amJvs.cpp` (de COM-naar-pipe-hook), MinHook-gebaseerde loaders, game-hooks onder `Games/ES3X` (Namco System ES3X: WMMT5/6, Star Wars, Machstorm, BanapassEmu, TouchEmu), `ES3B` (Pokken), `APM3`, `TypeX2/TypeX4`, `Europa-R`, `Nesica_Libs`, `Games/Other` (Raw Thrills FNF-reeks). Er is geen JVS-emulator in OpenParrot zelf: die zit in TeknoParrotUI (`JvsPackageEmulator.cs`). Er is geen gun-code voor onze games: geen Time Crisis 5, Transformers, Let's Go Safari, Luigi, Halo, JP of Terminator (grep naar wajv, Transformers, Safari, Luigi, ftdi gaf niets relevants).
- Bruikbaar als leesvoorbeeld: de COM-hook-reeks (welke Comm-functies een JVS-bibliotheek aanroept en wat hij terug moet krijgen); het gedeelde-geheugen-patroon; `pipehelper.c` (nuttig als specificatie van wat in een Wine-prefix nodig is).
- GPL-3 [afgeleid, geen juridisch advies]: overnemen of bewerken van code maakt het afgeleide werk GPL-3 zodra het wordt verspreid; voor eigen gebruik van de eigenaar speelt dat niet. Opties: (1) clean-room: het geheugenformaat en het JVS-protocol zijn feiten; de JVS-specificatie is publiek; schrijf onze eigen implementatie zonder de GPL-code open te hebben terwijl we implementeren, en leg vast wat we uit welke bron hebben (hier: het 64-bytes-formaat is als feit beschreven in dit document). (2) Een los hulpprogramma (bv. de Windows-helper in de prefix) onder GPL-3 uitbrengen met bron, en ravengund praat er via socket of gedeeld geheugen mee: dat is meestal "aggregatie" en laat de rest van de repo vrij. (3) De hele repo onder GPL-3 zetten; eenvoudig maar beperkend. Aanbeveling: optie 1 voor alles in de daemon, optie 2 alleen als we toch een stuk uit pipehelper.c willen hergebruiken. Segatools (Unlicense, uit eerder onderzoek) mag zonder voorwaarden als JVS-framing-referentie; TeknoParrotUI-code (GPL-3) niet zonder dit besluit.

## 4. Voorstel: gedeelde IO-brug in ravengund

Toestandsmodel (los van elk dialect)
- Per speler: aim (x, y in 0..1, ongeclampt, plus geldig-vlag), knoppen als vaste set (trigger, secundair/reload, grenade/pomp, start, vier extra, richting), analoge extra's (stuurwiel, hendel) als -1..1 of 0..1.
- Cabine: munt als teller van pulsen (niet als niveau), test, service, volume omhoog/omlaag.
- Uitgangen (van game naar daemon): recoil per speler (patroon + tijd), lampen (start, gun-led), later ticket. Doel: Move-rumble en led.
- Eén vertaalstap aan de rand, per dialect instelbaar: min/max, inversie, 8/16 bit, complement, byte-volgorde. Dat is de rol van `GunAnalogMath` in TP en komt overeen met onze `GunTransform`.

Dialecten en transporten (volgorde van bouwen)
1. `tp-shm` (nieuw): ravengund schrijft het 64-bytes-formaat per profiel (de vijf indelingen uit hoofdstuk 1) naar `/dev/shm/TeknoParrot_JvsState`, plus een eigen kleine Windows-helper in de prefix (named file mapping + spiegel, ~150 regels C, cross-compiler niet gecontroleerd). Effect: TPUI hoeft niet meer voor invoer te draaien, en de binding hangt niet meer van `eventN` af. De game-kant blijft TP. Dit is de eerste stap "zonder TeknoParrot-UI", niet "zonder kern".
2. `jvs-node` (nieuw, generiek): JVS v3-node met tabel per profiel (identificatie, schakelaarbits, analoge kanalen en bits, muntsleuven, algemene uitgangen), transport pty of pipe. Eerste doel: TC5 via Wine-COM-symlink naar een pty. Daarna LGS (vereist wel een hook voor `\\.\mxjvs`, zie 5).
3. `uhid-hid` (nieuw): virtueel HID-bord voor Transformers, nadat VID/PID en rapporten bekend zijn.
4. `tcp-plugin` (bestaat): Tomb Raider en Rabbids.
5. `ftdi-cmgr` en `nu-serial`: niet bouwen voordat het protocol gemeten is; waarschijnlijk niet haalbaar zonder echte hardware. Terminator, Halo en JP blijven op TP; Luigi laatst.

Volgorde voor de games van de eigenaar: (1) tp-shm voor alles wat nu op TP draait; (2) Transformers via uhid; (3) TC5 via jvs-node/pty; (4) LGS via jvs-node plus hook; (5) Raw Thrills-trio en Luigi pas bij nieuw inzicht. Dit stemt overeen met `docs/research/zonder-teknoparrot.md` §5, met als wijziging dat TC5 niet per se een eigen `wajvio.dll` nodig heeft als de originele DLL een seriële poort mag openen.

Wat per game onbekend blijft, en hoe te meten (alleen methode, niet uitgevoerd)
- Alle TP-games: of onze indeling van de 64 bytes exact genoeg is. Meting: terwijl een game draait, `/dev/shm/TeknoParrot_JvsState` (het spiegelbestand van TPUI, geen procesgeheugen) pollen met `xxd`, en bij het indrukken van één knop per keer de verandering noteren.
- TC5: of wajvio met een pty-COM-poort werkt (GetCommModemStatus op een pty kan falen, afgeleid), welk poortnummer, welke identificatie hij accepteert, en welk commandovolgorde. Meting: onze eigen node op een pty, alle ontvangen bytes met tijdstempel loggen; eerst een testprogramma met Wine dat de Comm-API's op het pty-symlink aanroept.
- Transformers: VID/PID, rapportindeling, kalibratieverloop. Meting: het uhid-apparaat dat we zelf maken laten loggen welke GET/SET-rapporten de game ons stuurt, en de eigen kalibratiestappen noteren; VID/PID uit publieke bronnen of de game-logs, niet door ontleden.
- LGS: welke IOCTL-codes naar `\\.\mxjvs`. Meting: een eigen proxy-DLL (via de DINPUT8-import) die CreateFile en DeviceIoControl logt; pas uitvoeren als de aanpak binnen de grenzen valt.
- Raw Thrills: het FTDI/cmgr-protocol en de led-berekening. Geen meetmethode zonder echte gun of USB-capture; nu niet haalbaar.
- Luigi: het protocol na de flash. Meting: een pty op COM1 en de bytes van `SendFlash` en de game loggen; antwoordbytes zijn onbekend, dus de flash zal waarschijnlijk niet slagen.

## 6. Transformers: Shadows Rising, wat de game echt zoekt (meting, 2026-10-09, avond)

Methode: statisch, alleen leesbewerkingen op de NAS. `Transformers2.exe` (32-bit PE, gewone secties .text/.rdata/.data, niet ingepakt, linkermap `TF2_Gun_R.map` past op de adressen) met `objdump -d`; de functies van `saebd.obj` (CSAEBoard, 0x57a130..0x57a7c0) zijn klein en gelezen. Verder `strings` en `objdump -p` van `Shell.exe` en `hidapi.dll`, en het proces onder Wine met `WINEDEBUG=-all,+dinput` (alleen het gameproces, zonder TeknoParrot erbij gestart). Alles [gelezen] tenzij anders gemerkt.

Gecorrigeerd: `Transformers2.exe` importeert alleen DINPUT8 (geen HID.DLL of SETUPAPI; die DLL's laadt Wine zelf voor DirectInput). De gun is dus geen "HID-IO-bord" voor de game maar een DirectInput-joystick. Het HID-IO-bord (`InitIOBoard`, `HIDioThread`) zit in `Shell.exe`.

CSAEBoard (de gun-invoer van de game):
- Aanmaken (`CSAEBoard::CSAEBoard(HWND)`): `DirectInput8Create(hinst, 0x0800, IID_IDirectInput8A)`, `CreateDevice(GUID_Joystick)` (de standaardjoystick van het systeem, GEEN filter op VID/PID of naam), `SetDataFormat(c_dfDIJoystick)`, `SetCooperativeLevel(hwnd, DISCL_NONEXCLUSIVE | DISCL_FOREGROUND)`, `EnumObjects(DIDFT_AXIS)` met een callback die per as `DIPROP_RANGE` -1000..1000 zet, `Acquire`. Geen feature- of uitvoerrapporten.
- Lezen (`Update`, 80 bytes DIJOYSTATE): speler 1 = (omrekening van lY, omrekening van lX), speler 2 = (omrekening van lRx, omrekening van lZ). Omrekening `(1000 - waarde) * 255 / 1000`: een as op -1000 geeft 510, op +1000 geeft 0. Links/boven is dus de lage kant van de joystick. De waarden gaan als 16-bit woorden (0..510) naar `GetP1GunAxis`/`GetP2GunAxis` en daarna door de eigen kalibratie van de game (`GetAdjstGunPos`).
- Knoppen: DirectInput-knop 0..3 = spelknop 0..3, DirectInput-knop 5 = spelknop 4 en DirectInput-knop 4 = spelknop 5 (omgedraaid). `IsButtonOn` = bit 7 van de knopbyte, `IsButtonPress` = op dit beeld aan en op het vorige uit. Gebruik in de speler-code [afgeleid]: speler 1 gebruikt knop 2 (aan en druk) en knop 0, speler 2 knop 3 en knop 1, beide spelers samen de knoppen 4 en 5. Wat welke knop is (start, trekker, hendels) is op de tv bepaald, zie hieronder.
- Verloren verbinding: `Poll` mislukt, dan `Acquire` in een lus zolang het resultaat `DIERR_INPUTLOST` is. Een apparaat dat tijdens het spel verdwijnt en terugkomt wordt dus niet betrouwbaar hervat.
- Recoil gaat niet naar dit apparaat: `SetP1RecoilFlag`/`SetP2RecoilFlag`/`SetShotRecoil` zetten vlaggen die `Update` als drie bytes (speler 1 of 2, aan/uit, patroon) in een bericht van type 15 naar een algemene verzendfunctie stuurt [afgeleid: dit is het kanaal naar de shell]. De shell logt het als "GAME_MSG_TRIGGER_RECOIL - Player 1 Started Recoil Pattern 1" in `Sega/shell/GameStateMachine - <datum>.log` en stuurt het naar het HID-bord via zijn recoildriver. Recoil naar rumble is daarmee nog niet gedaan (idee: dat logbestand volgen).

Het HID-IO-bord van de shell (alleen namen en foutmeldingen uit `Shell.exe`; niet ontleed):
- Het zoekt een HID-apparaat via SetupDi (`SetupDiGetClassDevs`, `...GetDeviceInterfaceDetail`), leest daarvan caps en een PID en versie, en voert dan een reeks commando's uit (`IOBOARD_INITIALISE`, `IDREQUEST1/2`, `UNLOCK1`, `COMMAND_UNLOCK2`, versie-aanvraag, "ENABLE KEYPAD"). De namen `IDREQUEST` en `UNLOCK` wijzen op een uitwisseling waarmee het bord zichzelf bekendmaakt of vrijgeeft. Dat valt onder de regel "geen beveiligings-, keychip- of dongle-controles onderzoeken of omzeilen": niet verder onderzocht, niet nagebootst. Zonder dit bord loopt de shell wel door (elke seconde de melding "Couldn't find IOBoard device" in `ioboard - <datum>.log`); de game start, het attract-scherm draait. Gevolg: lampen, het toetsenpaneel van de shell en de hardware-recoil van de shell blijven uit. VID/PID van dat bord: niet gezocht.
- `config.ini` van de shell: `[system] TEST=13 SERVICE=14` [afgeleid: knopnummers voor test en service op de joystick; of het 0- of 1-gebaseerd is staat niet vast].

Wine/DirectInput (gemeten): een uinput-joystick met 1209:72F0 verschijnt in Wine als `HID\VID_1209&PID_72F0` (winebus, evdev-pad; geen /dev/uhid nodig). `CreateDevice(GUID_Joystick)` geeft de joystick met joystick-id 0, en die was tot nu toe de PS Move zelf (VID 054C, PID 03D5, door Wine via hidraw als joystick gezien; de ids staan per product in `HKCU\System\CurrentControlSet\Control\MediaProperties\PrivateProperties\DirectInput\...\Calibration\N`, waarde "Joystick Id"). Dat verklaart de eerdere waarneming "vizier zit in de hoek, de X-as doet niets": de game las de ruwe Move-assen. `scripts/wine-joyid.sh PREFIX 1209:72F0` geeft ons bord id 0 en schuift andere apparaten op.

Direct starten: `Transformers2.exe` zonder shell blijft staan op "SYSTEM INITIALIZING... LOADING.." (meer dan 50 s gemeten); hij wacht kennelijk op de shell (de shell sluit zichzelf voor het starten en start de game, `Mainthread - <datum>.log`: "Closing down shell ready for game launch"). De shell is er dus nodig, en die draait onder TeknoParrot (dongle in `DK2WIN32.dll`, kern in `Shell.exe`): dat blijft zoals het was.

Live-uitkomst (dezelfde nacht, op de tv): met het virtuele bord als joystick-id 0 start de game normaal via de shell (laden ongeveer 3,5 minuut), toont "PRESS START BUTTON / FREE PLAY", start met toets 1 (de log van de shell meldt `GAME_MSG_START_PRESSED - Player 1` en `GAME_MSG_STAGE_START`), de trekker schiet (`GAME_MSG_CURRENT_SCORE`), en het wapen en het spoor van de kogels volgen de vier hoeken van een testpatroon (`test-pattern corners --dwell`; een vastgehouden toets of knop blijft alleen bestaan zolang een testpatroon draait, anders geeft de live Move ze na ongeveer 4 ms weer vrij: in het spel zelf houdt de speler de knop met de Move vast). Het bereik (de game rekent intern 0..510) en een zichtbaar vizier zijn niet gemeten; de kalibratie van de game en het testmenu (TEST=13, SERVICE=14 in `config.ini`) zijn niet geopend: de knoppen 12 en 13 als joystickknop deden niets. Open: wat TEST en SERVICE in de shell lezen, de hendelknoppen (4 en 5), speler 2 (assen Z en RX), en recoil via het logbestand van de shell.
